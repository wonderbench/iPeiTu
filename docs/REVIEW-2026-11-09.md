## 发现

按影响从高到低排列。

### 高：实机验收严重滞后，设计前提未核实

- 依据：`docs/V03-PLAN.md`“实机待验清单”，共 6 项沿用欠账和 15 组新增项目。
- 第 1 项写明“这一项决定步骤 2 的方案，建议在步骤 3 开发前核对”。实际上步骤 3（填入）、4a（连续配图、清除标记）都依赖 `AlternativeText` 标记，已经合并。如果 WPS 保存 DOCX 后丢失替代文字，已填框无法再识别，清除标记和“下一个空框”都会失效，需要返工。
- 第 4 项 `WindowSelectionChange` 只见于第三方类型声明。填入时窗格能否及时识别选中的框，目前依赖焦点和鼠标移入刷新，未实测。
- 排版十项和表格宽度直接改写文档格式，只有模拟宿主证明调用契约。删除空行、清除空格等操作在真实文档中的边界情况风险较高。
- 建议：下一步按清单第 1、10、11 项优先实机核对，再验排版与安装。结果写入单独的验收文档，和模拟结果分开记录。

### 中：局域网模式以明文 HTTP 传输访问密钥

- 位置：`server/http.js` 的 `validateRemote`，`server/lan-client.js` 的 `headers()`。
- 密钥校验本身做得好：比较 SHA-256 摘要并用常数时间比较，拒绝带浏览器来源标头的请求，远程只开放图库、素材、上传和知识库接口，远程健康检查不返回进程号和路径。
- 问题：连接是明文 HTTP，同一网段能抓包的人可以取得密钥。取得密钥后拥有全部远程权限：上传、修改素材信息、移入回收站、编辑知识库。没有角色，也不能单独吊销某台客户端，只能更换全局密钥。
- 次要：认证失败时每次都写一行警告日志（`http.js` 中的 `console.warn`），服务日志按追加方式写入、没有轮转（`scripts/service.ps1` 的 `--log`）。服务器长期运行或被扫描时，日志会持续增长。
- 建议：在 README 的局域网部署一节写明只用于可信的专用网络，并说明怎样更换密钥。日志按大小轮转，或对同一来源的失败只记一次。HTTPS 和按客户端授权可放到步骤 12 一并考虑。

### 中：生成的缓存没有清理机制

- 位置：`server/fit.js`（`fitted/`）、`server/insertion-quality.js`（`insertion/`）、`server/placeholder.js`、`server/lan-client.js`（`lan-cache/`）。
- 这些目录只写入，没有淘汰或清理的代码。适配图的缓存键包含框的宽高和适配方式，每个尺寸不同的框都会多生成一份文件。客户端的 `lan-cache` 同样只增不减。
- 影响：不会出错，但图库目录会随使用时间持续增大，用户也没有入口可以清理。
- 建议：提供“清理缓存”操作，或按最后访问时间、总大小淘汰。缓存都能重新生成，清理风险低。

## 做得好的地方

- **本机服务的来源校验。** 本机请求同时校验回环地址和 Host，并检查 Origin、`Sec-Fetch-Site`、Referer，可以防 DNS 重绑定和跨站请求。静态文件先解析真实路径，再确认位于 `public/` 内。
- **输入严格校验。** 接口参数用白名单，不允许重复，JSON 字段必须完全匹配，请求体有大小上限，图片限制字节数和像素数。
- **持久化稳妥。** 索引、收藏、知识库、连接配置都先写临时文件再替换。文件损坏或版本不明时拒绝读取并保留原文件，不悄悄重建。旧版索引迁移前先写备份。
- **不掩盖失败。** 前端的 `catch` 都会给出提示或计数。WPS 写入后回读核对，不一致时提示撤销。局域网下载核对字节数和 SHA-256。
- **前端没有注入风险。** `innerHTML` 只用于固定的图标 SVG，没有拼接用户数据。
- **验收记录诚实。** 每个 PR 都区分模拟通过与实机待验，没有把模拟结果写成实机验收，符合 `AGENTS.md` 的要求。
- **CI 覆盖。** Ubuntu 和 Windows 都运行测试，Windows 上实际测试安装脚本；作业设置了超时；抽查的 PR 都在 CI 完成后才合并。
