## 我理解的产品目标

iPeiTu 是给标书编制人员用的 WPS 文字加载项，让“给标书配图”从找图、插图、调尺寸的重复劳动，变成放框、点图两步。

- **核心流程**（V03-PLAN 开头的三件事）：管理素材，在文档里放占位框，按框的尺寸填入图片。
- **周边能力**：一键排版和表格整理、标书知识库（通用文字片段）。它们让加载项从配图工具扩展成标书编制工具箱。
- **使用范围**：从一个人的本机图库，到一间办公室共用的局域网图库，再到团队云图库。
- **用户**：工程类投标的编制人员，不是开发者。他们在赶标书时使用，文档经常有几百页。

衡量方案好坏的标准是：一份标书配完图需要多少时间和多少次点击，以及一位同事拿到它之后能不能自己装上、用起来。

如果这段理解有偏差，请先纠正，后面的优先级会跟着变。

## 结论

1. **功能面已经够宽，下一步应该把核心流程做深。** 目前“框和图怎么对上”还完全靠人：按框名检索只是把框名原样填进检索框，名称多一个字就搜不到（见实测）。按名称和比例自动推荐候选图，是离产品目标最近的一步。
2. **用一个“实机自检页”还清验收欠账。** 开发机没有 WPS，待验清单已有 6 项沿用欠账和 15 组新增项目，靠人工逐项核对很难跟上。清单里大部分是“某个接口在真实 WPS 里的行为”，可以由加载项在一份新建的空白文档里自动跑完并生成报告，你只需要在装有 WPS 的电脑上点一次。
3. **分发是同事用不上的主要障碍。** 现在要先装 Node.js 24，安装时还要联网下载依赖。建议由 CI 产出自带运行环境的压缩包，解压后双击即可安装。
4. **素材库要为几千张图做准备。** 2000 张时窗格一次渲染 2000 张卡片，列表总高约 19.6 万像素，每次检索都重新下载缩略图。分页加载和缩略图缓存改动不大，效果明显。
5. **排版工具需要“全文操作先确认”。** 现在没有选中内容时，点一下“去除表格线”就会改动全文所有表格，没有确认，也不预告影响范围。
6. **三个模块可以连成一条线。** 知识库片段里写 `【图：名称】`，插入后转成占位框，再按框名推荐素材。每一段现在都已具备，只差衔接。

## 现状与目标的差距

| 目标 | 现状 | 差距 |
| --- | --- | --- |
| 便捷管理素材 | 导入、去重、分类、标签、批量整理、回收站都已具备 | 大图库下的浏览性能；分类只有一层；没有永久删除和占用统计 |
| 在合适位置放占位框 | 光标处插入、文字标记批量转换 | 照片表（4b）未定；尺寸选择不记忆；框不带图题 |
| 便捷填充并适配尺寸 | 三种适配方式、自动跳到下一个空框、比例优先 | 候选图要人工检索；不提示同一张图已在本文用过 |
| 标书格式管理 | 十项一键排版、表格宽度 | 全文操作无确认；没有针对具体招标要求的格式方案 |
| 标书内容复用 | 知识库的分类、维护、插入 | 冷启动要逐条录入；工程类别写死为四类；只支持纯文字 |
| 同事共用 | 局域网图库 | 安装门槛高；本机图库不能带着标签迁到服务器 |
| 可信赖 | 输入校验、原子写入、回读核对做得扎实 | 实机行为大面积未验证；索引没有滚动备份 |

## 本次实测

环境：Linux 容器，Node 22.23.4（项目要求 24，CI 使用 24），无头 Chromium，窗格宽 420 像素。图库为 2000 张自行生成的临时图片，测试后已停止服务。

| 项目 | 结果 |
| --- | --- |
| `npm run check` | 通过 |
| `npm test` | 197 项：191 通过、0 失败、6 跳过（Windows 专用） |
| `/api/library` 一次返回的数据量 | 2000 张时 970 KB；用合成索引测得 5000 张约 2.6 MB，10000 张约 5.3 MB |
| 服务端列表与检索耗时 | 10000 张时全量列表约 37 毫秒、检索约 23 毫秒，不是瓶颈 |
| 写索引耗时 | 10000 张时每次约 37 毫秒；导入时每张图写一次 |
| 窗格首屏 | 2000 张卡片一次生成，共 26370 个页面节点，列表总高 196012 像素 |
| 缩略图请求 | 检索“脚手架”得到 200 张，重新请求 196 张缩略图；清空检索后 0.8 秒内重新请求 951 张 |
| 切换视图回到“全部” | 约 0.7 秒 |
| 按框名检索 | 图库有 200 张“脚手架搭设示意图-N”，检索“脚手架搭设施工”得到 0 张 |
| 按分类名检索 | 分类“机电安装”下有 250 张，检索“机电安装”得到 0 张 |

缩略图重复请求的原因是所有响应都带 `Cache-Control: no-store`（`server/http.js:112`）。WPS 内嵌浏览器的懒加载行为可能与无头 Chromium 不同，实际请求数需要实机确认。

## 方案

每项标注工作量（小、中、大）和是否需要你先决定。

### A. 实机自检页

**现状。** V03-PLAN 的实机待验清单有 6 项沿用欠账和 15 组新增项目。其中多数是接口行为问题，例如：

- `AlternativeText` 在保存重开后是否保留（第 1 项，决定占位框方案）。
- `Cell.Height` 和 `HeightRule` 在合并单元格上是否可靠（第 2 项）。
- `WindowSelectionChange` 事件能不能用（第 4 项）。
- 200 张图时遍历 `InlineShapes` 要多久（第 5 项）。
- 内置样式编号 `-2`—`-10` 能否设为“标题 1—9”（第 14 项）。

这些都可以由代码判断，不需要人看。

**建议。** 在加载项里增加一个“自检”页面（功能区放一个小按钮，或从素材库的“更多”进入）：

- 点击后新建一份空白文档，只在这份文档里操作，不碰任何已打开的标书。
- 依次执行各项探测，写入、回读、保存到临时目录、关闭、重开、再回读。
- 输出一份可复制的文本报告：WPS 版本、每项的通过或失败、实测数值、耗时。
- 报告贴回仓库的验收文档，和模拟结果分开记录。

仍需要人看的项目（窗格渲染、防火墙弹窗、两台电脑互连、拖拽）留在清单里，自检页把它们列成“请目视确认”的步骤。

**价值。** 一次点击覆盖清单的大部分。以后每个涉及 WPS 的步骤都给自检页加一项，欠账不再累积。自检结果还可以反过来校准测试里的模拟宿主。

工作量：中。不需要你决定范围，但需要你在装有 WPS 的电脑上运行。建议排在所有新功能之前。

### B. 核心配图流程

**B1. 选中占位框时自动推荐候选图。**

- 现状：`public/app.js:1039` 的“按框名检索”把框名原样填入检索框。服务端检索要求每个词都是名称、别名或标签的子串（`server/library.js:321`），所以框名和图名只要差一个字就没有结果（见实测）。
- 建议：服务端增加按相似度排序的查询。用框名与名称、别名、标签、分类的二字片段重合度打分，再叠加比例接近程度。选中框时图库直接按这个顺序显示，前几张标出“名称匹配”。没有匹配时退回原顺序，并说明没有找到名称相近的图。
- 这不改变“由人点击填入”的规则，只改变图的排列顺序。
- 工作量：中。需要你确认：选中框时默认按推荐排序，还是保留手动开关。

**B2. 检索覆盖分类，结果按相关度排序。**

- 现状：分类不参与检索（见实测）；结果按导入顺序排列，名称完全相同的图也可能排在很后面。
- 建议：检索范围加入分类；排序依次为名称完全匹配、名称开头匹配、名称包含、别名、标签和分类。
- 工作量：小。

**B3. 标出“本文已用”。**

- 现状：已填的占位框标记里有素材 ID（`public/wps-bridge.js` 的 `placeholderMarker`），扫描文档时已经能读到。但图库不提示，同一张图在一份标书里用两次不容易发现。
- 建议：扫描结果里汇总已用素材 ID，在对应卡片上标“本文已用”。普通插入的图片目前没有标记，是否也写入标记取决于自检第 1 项的结果。
- 工作量：小。

**B4. 交付前检查。**

- 现状：未填的框会随文档打印；已填框的标记要手动点“清除标记”；正文里可能还有没转换的 `【图：名称】`。这三件事分散在占位框面板的不同位置。
- 建议：增加一个“交付检查”按钮，一次列出未填的框、残留的文字标记、仍带插件标记的图片、同一素材重复使用的位置，每项可以点击定位。全部通过后再提供“清除标记”。
- 工作量：中。

**B5. 照片表（步骤 4b）的默认做法。**

- 现状：等待你确认做法，已阻塞步骤 4b 和步骤 9 的一部分。
- 建议的默认做法，你同意即可开工：
  - 选择列数（2、3、4）和行数，生成一张表格。
  - 每个图片单元格放一个“填满单元格”的占位框，下面一行是图题文字，默认取框名。
  - 图片行使用固定行高，保证同一行的图一样高。
  - 填入沿用现有流程。
- 固定行高单元格里的图片是否被裁切，是清单第 9 项，需要自检页先核对。
- 工作量：中。需要你确认。

**B6. 占位框的小改进。**

- 记住上次选择的尺寸（现在每次打开都回到“整行宽”）。
- 允许保存两三个自定义常用尺寸。
- 框可以带图题段落，图题取框名。是否自动编号属于“本轮暂不做”的范围，需要你决定。
- 工作量：小。

### C. 素材库在大图库下可用

**C1. 分页加载。**

- 现状：`/api/library` 每次返回全部素材，`renderAssets`（`public/app.js:439`）一次生成全部卡片；每敲一个字都清空并重画整个列表（`scheduleSearch`，`public/app.js:630`）。
- 建议：接口增加 `limit` 和 `offset`，返回匹配总数。窗格先渲染第一屏，滚动到底部再取下一页。分类数量等统计单独请求，检索时不必每次重算。
- 工作量：中。

**C2. 缩略图和原图允许缓存。**

- 现状：所有响应都是 `no-store`。素材 ID 就是文件内容的 SHA-256，同一个地址的内容不会变。
- 建议：`/api/assets/{id}/thumbnail` 和 `/image` 改为长期缓存（`private, max-age=31536000, immutable`），其余接口保持 `no-store`。局域网模式下，缩略图现在每次都经本机服务转发到服务器，缓存后可以明显减少局域网流量。
- 工作量：小。

**C3. 导入时合并写索引。**

- 现状：目录导入每导入一张图就完整重写一次 `index.json`（`server/library.js:526`）。10000 张的图库每次约 37 毫秒，导入一个大目录时累计可达数分钟。
- 建议：目录导入按批写入（例如每 50 张或每 2 秒），任务结束时再写一次。中途崩溃时，还没写进索引的图片在下次导入时会重新登记，图片文件按哈希覆盖，不会出现重复或残缺的记录。
- 工作量：小到中。优先级低于 C1、C2。

**C4. 存储管理。**

- 现状：没有永久删除，回收站只增不减；导入会复制原图，图库占用持续增长；用户看不到图库占了多少空间。四类缓存没有清理入口（11-09 审查已指出）。
- 建议：在“更多”里增加“图库占用”，显示原图、缩略图、缓存、回收站各占多少，提供“清理缓存”和“清空回收站”。清空回收站是永久删除，需要二次确认，并且局域网模式下只允许在服务器本机操作。
- 工作量：中。永久删除需要你确认。

**C5. 分类与标签的整理。**

- 现状：分类是一层扁平的文字。文件夹导入会产生“房建/主体结构”这样的名称，在窗格里只是一长排横向滚动的按钮。改一个分类名要用批量整理先加后删。
- 建议：
  - 把名称里的“/”当作层级显示，先选上一级，再显示下一级，和知识库的“类别、章节”一致。
  - 增加“重命名分类”和“合并标签”，一次改动全库。
- 工作量：中。

**C6. 本机图库迁移到局域网图库。**

- 现状：切到局域网后“两边的数据不合并”。每个人此前在本机整理的名称、别名、标签，只能从原始文件夹重新导入，而导入只带文件名和文件夹分类，其余信息丢失。
- 建议：在“图库来源”里增加“把本机图库上传到服务器”，逐张上传并带上名称、别名、分类和标签；服务器上已有相同内容时合并这些信息，不覆盖。
- 工作量：中。

### D. 交付与分发

**D1. 自带运行环境的安装包。**

- 现状：`scripts/setup.ps1` 要求先安装 Node.js 24，版本不符直接退出；依赖缺失时运行 `npm ci`，需要联网下载 `sharp` 的预编译文件。办公网络限制外网或同事不熟悉这些操作时，安装就卡住。
- 建议：
  - 在 GitHub Actions 增加发布流程：打标签时，在 Windows 上安装生产依赖，连同便携版 `node.exe` 打成一个压缩包，作为 Release 附件。
  - `service.ps1` 和 `setup.ps1` 优先使用包内的 `node.exe`，没有时才找系统的 Node.js。
  - 使用说明变成“下载、解压、双击安装.cmd”，不需要装 Node，也不需要联网。
- 之后可以再考虑图形安装程序和代码签名。
- 工作量：中。Release 是对外发布动作，需要你确认。

**D2. 升级。**

- 现状：更新代码前要手动停止服务，覆盖文件后再启动。
- 建议：增加“升级.cmd”，依次停止服务、核对新旧版本、启动服务、提示重开 WPS。窗格的“更多”里显示当前版本。
- 工作量：小。

**D3. 服务未运行时给出明确提示。**

- 现状：
  - 任务窗格页面由本机服务提供。服务没有运行时，窗格里是浏览器的“无法访问”页面，用户不知道该做什么。
  - `public/main.js:7` 的 `openPane` 直接创建窗格，不检查服务。
  - 服务进程意外退出后没有自动重启。`server/index.js` 没有处理未捕获的异常，后台运行时这类错误不会写进日志文件，事后查不到原因。
- 建议：
  - `openPane` 先请求 `/api/health`，失败时提示“本地图库没有运行，请双击启动.cmd”。
  - 服务进程记录未捕获的异常后退出；自动启动改为带重启策略的计划任务，或由一个很小的守护循环拉起。
- 如果服务在 WPS 启动时就没有运行，功能区本身能否加载需要实机确认，可以加入自检清单。
- 工作量：小到中。

**D4. 诊断信息。**

- 建议：“更多”里增加“复制诊断信息”，包含版本、WPS 版本、图库统计、最近的错误日志。同事遇到问题时发给你即可，不必远程查看。日志需要先有大小上限（11-09 审查已指出）。
- 工作量：小。

### E. 排版工具

**E1. 全文操作先确认。**

- 现状：`public/layout-tools.js:36` 用“有没有选中内容”决定作用范围，没有选中时作用于全文。`public/format.js:55` 点击后立即执行。范围只在窗格顶部用一行小字说明。在一份几百页的标书里误点“去除表格线”，只能靠撤销。
- 建议：
  - 作用于全文时，先统计影响范围，弹出确认，例如“将去除全文 46 个表格的边框”。作用于所选内容时直接执行。
  - 范围做成窗格顶部的明确开关（所选内容、全文），不再从有无选区推断。这会改动步骤 7 已采用的规则，那条规则本身也在“待用户确认”里。
- 工作量：小。需要你确认。

**E2. 大文档的耗时。**

- 现状：边距清零、去除底纹等操作逐个单元格调用 WPS 接口。几百个表格的标书可能要等很久，期间窗格没有进度，也不能取消。实际耗时未知。
- 建议：先在自检页里测 200 个表格的耗时。超过几秒时，改为按表格分批执行并显示进度；分批后一次撤销是否仍然有效，也要在自检页核对。
- 工作量：取决于实测。

**E3. 常用组合。**

- 建议：把若干操作存成一个组合，一次执行，例如“删除空行、表格宽度、表格居中、首行缩进”。组合保存在本机。
- 工作量：小到中。

**E4. 格式方案。**

- 现状：原计划的“格式方案管理与样式应用”已被十项排版工具取代，列在“本轮暂不做”。
- 判断：十项工具解决的是清理，投标更常见的要求是“按招标文件规定的字体、字号、行距统一全文”。建议在步骤 9、10 之后，把“格式方案”重新列为候选：保存一组样式定义，一键套用，并检查全文偏离之处。
- 工作量：大。需要你决定是否恢复这个方向。

### F. 知识库

**F1. 从已有标书批量收录。**

- 现状：只能逐条新建，或选中一段后“收录选中内容”。知识库不预置正文，冷启动成本全在用户身上。
- 建议：增加“按标题拆分收录”。打开一份以前的标书，选择按“标题 2”或“标题 3”拆分，列出将生成的片段（标题、字数、建议的类别和章节），勾选后一次收录。超过正文上限的片段单独列出，不截断。
- 工作量：中。

**F2. 工程类别可以自定义。**

- 现状：四个工程类别写死在 `server/knowledge.js:7`，章节可以自填，类别不能。做水利、园林、电力、装修的团队用不上。
- 建议：类别和章节建议保存在 `knowledge.json` 里，可以增删改名；现有四类作为初始值。文件版本升到 2，升级前按图库索引的做法先备份。
- 工作量：中。

**F3. 导出与导入。**

- 建议：知识库导出为一个文件，在另一台电脑或另一个团队导入，按标题和正文去重。这样可以由一个人整理好再分发。
- 工作量：小到中。

**F4. 片段里的配图标记。**

- 现状：11-08 你决定知识库“不做可替换字段和配图标记”。之后步骤 4a 交付了“文字标记转占位框”：正文里的 `【图：名称】` 可以批量转成占位框。片段正文是纯文字，现在写入 `【图：脚手架搭设】` 已经可以走通“插入片段、转占位框、填图”。
- 建议：不新增语法，只做衔接。插入的片段含有文字标记时，提示“片段含 3 个配图标记”，并提供“转为占位框”。配合 B1，这段文字对应的图会自动排在前面。
- 工作量：小。这与 11-08 的决定有关，需要你确认是否采纳。

**F5. 带格式的片段。**

- 现状：片段是纯文字。工艺工法里常见的表格、加粗和图片都带不进来。
- 建议：先调查 WPS 是否提供可靠的“带格式复制范围”或“插入文件”接口，再决定是否做。调查结果写入接口依据。
- 工作量：未知，先调查。

### G. 团队共享路线

**现状。** 步骤 14 的局域网图库已经实现素材和知识库共享。步骤 12 的团队云图库要做账号、角色、会话和跨团队隔离，工作量大，而且目前没有服务器。

**建议。** 把步骤 12 拆成在局域网图库上逐步加固，每一步都能独立交付：

1. **两种密钥。** “使用”密钥只能浏览、检索、插图；“管理”密钥可以导入、整理、删除。这是最便宜的角色区分。
2. **按客户端管理。** 服务器列出连接过的客户端，可以单独停用，不必更换全局密钥。
3. **可选的加密连接。** 服务器生成自签名证书，客户端首次连接时确认指纹。
4. **本机缓存素材信息和缩略图。** 服务器不在线时仍可浏览和检索，插图时再提示需要连接。

只有出现跨办公室、跨网络的需求时，再做真正的云端服务。

工作量：每步小到中。需要你确认步骤 12 是否按这个方向调整。

### H. 数据安全与可维护性

**H1. 索引和知识库的滚动备份。**

- 现状：`index.json` 和 `knowledge.json` 各只有一份。写入是先写临时文件再替换，能防写到一半；但程序缺陷或误操作造成的错误内容会直接覆盖。图片文件以哈希命名，索引一旦出错，名称、分类、标签都无法从文件恢复。知识库正文是手工录入的，更难重来。
- 建议：每天第一次写入前，把当前文件复制到 `backups/`，各保留最近 7 份。提供“从备份恢复”的说明。
- 工作量：小。

**H2. 写入后落盘。**

- 现状：`replaceFile`（`server/library.js:169`）和 `persist`（`server/library.js:245`）写完临时文件后直接改名，没有先同步到磁盘。断电时有可能留下内容不完整的文件。
- 建议：改名前对临时文件调用同步。
- 工作量：小。
